# 版本演进与兼容性规范

## 1. API 版本策略

### 1.1 URL 路径版本

- 所有对外接口统一使用路径版本：`/api/v1/resource`
- 新建业务模块默认从 `v1` 开始
- 版本升级时，旧版本至少保留 **6 个月** 过渡期

### 1.2 版本升级规则

| 变更类型      | 版本升级                | 示例                          |
| ------------- | ----------------------- | ----------------------------- |
| 新增字段/接口 | 次版本号 +1 (v1 → v1.1) | 新增 `user.v2/nickname`       |
| 字段类型变更  | 主版本号 +1 (v1 → v2)   | `user.id` 从 Long 改为 String |
| 删除字段/接口 | 主版本号 +1 (v1 → v2)   | 删除 `user.legacyField`       |
| 语义变更      | 主版本号 +1 (v1 → v2)   | `GET /count` 返回含义改变     |

### 1.3 废弃标记

```java
@Deprecated(since = "1.2", forRemoval = true)
@GetMapping("/api/v1/users")
public R getUserV1() { ... }

@GetMapping("/api/v2/users")
public R getUserV2() { ... }
```

- 废弃接口必须添加 `@Deprecated` 注解并标注 `since` 版本
- 废弃接口必须在 OpenAPI 文档中标记为 deprecated
- 保留期间内，新客户端必须使用新版本接口

## 2. 数据库迁移管理

### 2.1 迁移工具选择

- **选型**：Flyway（社区成熟，Spring Boot 原生支持）
- **备选**：Liquibase（支持 XML/YAML 格式，团队熟悉度较低）

### 2.2 迁移脚本规范

```
src/main/resources/db/migration/
├── V1__init_schema.sql          # 初始化建表
├── V2__add_user_role.sql        # 增量变更
├── V3__alter_order_table.sql    # 表结构变更
└── R__seed_data.sql             # 参考数据（以 R 开头可重复执行）
```

### 2.3 命名规则

| 前缀          | 用途             | 执行策略                           |
| ------------- | ---------------- | ---------------------------------- |
| `V{版本号}__` | 版本化迁移       | 只执行一次，严格按版本号顺序       |
| `R__`         | 可重复执行的脚本 | 每次启动都会执行（参考数据、视图） |
| `U{版本号}__` | 回滚脚本（可选） | Flyway 默认不启用，手动执行        |

### 2.4 迁移脚本编写要求

- ✅ **幂等性**：脚本必须可重复执行，使用 `IF NOT EXISTS` / `IF EXISTS`
- ✅ **版本号唯一**：每个版本号对应一个脚本，禁止修改已提交的 V 开头脚本
- ✅ **向后兼容**：新增字段必须允许 NULL 或有默认值；删除字段必须先代码下线再删表
- ✅ **注释完整**：每个脚本头部注明变更原因和影响范围
- ❌ **禁止 DDL + DML 混合**：结构变更和数据变更分离到不同脚本

### 2.5 数据迁移流程

```
1. 编写迁移脚本（V{N+1}__xxx.sql）
2. 本地测试 → 确认脚本可执行
3. 代码提交 → 脚本与代码一起提交
4. 部署上线 → Flyway 自动执行迁移
5. 验证 → 确认数据完整性
```

### 2.6 破坏性变更处理

当表结构发生破坏性变更时（如删除字段、修改类型）：

1. **软迁移**：先在 Java 代码中停止使用该字段，保留数据库列
2. **过渡脚本**：编写 `V{N+1}__deprecate_xxx.sql` 标记废弃
3. **硬删除**：下个版本再编写脚本物理删除

## 3. 配置管理规范

### 3.1 配置文件分层

```
src/main/resources/
├── application.yml              # 通用配置（默认值）
├── application-dev.yml          # 开发环境
├── application-test.yml         # 测试环境
├── application-prod.yml         # 生产环境
└── application-local.yml        # 本地环境（加入 .gitignore）
```

### 3.2 配置变更原则

- ✅ **向前兼容**：新增配置项必须提供默认值，旧配置文件无需修改即可运行
- ✅ **标记废弃**：废弃配置项使用 `@Deprecated` 标记，并在启动时打印警告日志
- ✅ **集中管理**：业务相关的配置集中在 `app.*` 命名空间下
- ❌ **禁止删除**：废弃配置至少保留 **2 个版本周期**

### 3.3 配置版本记录

每次发布新版本时，在 `CHANGELOG.md` 中记录：

```markdown
## v1.2.0 (2026-08-15)

### 新增配置

- `app.features.export.enabled`：控制导出功能开关（默认 true）

### 废弃配置

- `app.cache.ttl-seconds`：已废弃，改用 `app.cache.ttl`（支持 Duration 格式）
```

## 4. 变更日志规范

### 4.1 CHANGELOG 格式

Keep a Changelog 格式，按版本倒序排列：

```markdown
## [Unreleased]

### Added

- 新增 Excel 导出公共组件 `ExcelExportService`

### Changed

- `R.error()` 方法签名变更，新增错误码参数

### Deprecated

- `UserController.listUsers()` 已废弃，请迁移至 `UserController.pageUsers()`

### Fixed

- 修复分页查询在大数据量下的性能问题

### Removed

- 删除 `LegacyPaymentService`，请迁移至 `PaymentStrategyFactory`
```

### 4.2 变更类型定义

| 类型       | 说明             | 影响范围       |
| ---------- | ---------------- | -------------- |
| Added      | 新增功能         | 向下兼容       |
| Changed    | 已有功能的变更   | 可能需要适配   |
| Deprecated | 即将废弃的功能   | 无立即影响     |
| Removed    | 已废弃功能的移除 | **破坏性变更** |
| Fixed      | Bug 修复         | 向下兼容       |
| Security   | 安全修复         | 建议立即升级   |

## 5. AI 协作确认机制

### 5.1 需要确认的变更（先展示方案再动手）

以下变更必须先展示方案（含影响范围、迁移成本、回滚方案），再征求确认：

- 数据库表结构变更（新增/删除/修改字段）
- API 签名变更（请求/响应结构变化）
- 新增第三方依赖（pom.xml 改动）
- 超过 **50 行** 的重构代码
- 公共组件的接口变更

### 5.2 确认流程

```
1. AI 提出变更方案（影响范围 + 迁移成本 + 回滚方案）
2. 展示【当前状态】→【目标状态】对比
3. 用户确认后再实施
4. 实施后同步更新 CHANGELOG
```

### 5.3 变更风险评估

AI 在提出变更时必须标注风险等级：

- 🟢 **低风险**：纯新增代码，不影响现有功能
- 🟡 **中风险**：修改现有接口，可能影响调用方
- 🔴 **高风险**：数据库变更、删除功能、框架升级

高风险变更必须提供完整的回滚方案。
