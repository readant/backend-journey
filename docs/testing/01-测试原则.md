# 01 测试原则

> 写测试之前先想清楚三件事：**为什么测、测什么、怎么测**。这一篇给结论，后面的篇章给方法。

## 1. 为什么测（价值排序）

| 价值 | 说明 | 对应实践 |
| ---- | ---- | -------- |
| **防回归** | 改一处代码，确认没弄坏别处 | 核心 Service 必须有测试，重构后跑一遍 |
| **锁定契约** | 方法的行为（含异常、边界）被固定下来 | 异常分支、默认值分支专门写用例 |
| **倒逼设计** | 测不动的代码往往设计有问题 | 方法太长、分支太杂、依赖太多，先重构再测 |
| 文档作用 | 用例即说明书：读测试就能知道方法该有什么行为 | `@DisplayName` 写中文行为描述 |

> 判据：**一行用例至少对应一条「这条业务规则不能坏」**。为凑覆盖率写的用例没有价值。

## 2. 测什么（覆盖优先级）

```
✅ 必须覆盖  Service 层核心业务逻辑（分支 / 异常 / 边界）
✅ 建议覆盖  工具类、公共组件（R、异常处理器、TokenService 等）
⚠️ 可选     简单 CRUD 的 Mapper
❌ 不需要   Spring 配置类、Lombok 生成的方法
```

为什么 Service 层最优先：

1. **业务规则集中地** —— 状态流转、默认值、存在性校验、组装逻辑全在这一层
2. **边界清晰** —— 上游 Controller 只做参数透传，下游 Mapper 只做 SQL
3. **好 Mock** —— Mapper 是接口，打桩成本低，跑得快（毫秒级）

边界条件的枚举方法，每个方法问自己三个问题：

| 问题 | 示例 |
| ---- | ---- |
| 正常路径有几种走法？ | 创建文章：不传状态 / 传状态 → 两种结果 |
| 非法输入会怎样？ | 父栏目不存在 / 文章不存在 → 抛异常 |
| 空数据边界呢？ | 无数据返回空列表 / 列表为空时字段为 null |

## 3. 怎么测（三条铁律）

### 铁律一：given-when-then 三段式

```
given  准备数据（构造入参 + 打桩 Mapper 返回值）
when   调用被测方法（一行）
then   断言结果（AssertJ 断言 + verify 验证交互）
```

三段用空行隔开，**when 只能有一行调用**。调用被测方法前所有准备都在 given，之后所有验证都在 then。

### 铁律二：一个用例只验证一个行为

一条分支一个用例，用例之间互不依赖。宁可 20 个小用例，不要 3 个大用例各测一堆事 —— 前者失败时一眼定位到规则，后者失败时要人肉排查。

### 铁律三：不测框架，不测实现细节

- ❌ 不验证 Mapper 的 SQL 写没写对（那是集成测试的事）
- ❌ 不断言 Mock 桩之外的方法内部实现步骤
- ✅ 只断言「输入 → 输出的行为契约」

## 4. 测试金字塔（知道即可）

```
       / 集成测试 \       少量：起 Spring 容器，验证跨层协作
     /  单元测试  \      大量：本仓库主攻方向，毫秒级、稳定
   /  Mapper 测试  \     适量：MyBatis-Plus 的 SQL 正确性
```

本仓库的 74 个用例集中在「单元测试」一层 —— 快、稳、能防回归。集成测试在后续项目引入外部依赖（Redis、ES）时再展开。

## 5. 命名规范（来自规则，必须遵守）

| 对象 | 规范 | 示例 |
| ---- | ---- | ---- |
| 测试类 | `{被测类名}Test` | `CategoryServiceImplTest` |
| 测试方法 | `should{预期行为}_when{条件}` | `shouldThrow_whenParentMissing` |
| 展示名 | `@DisplayName` 写中文行为 | `"父栏目不存在 → 抛出业务异常 400"` |
| 组织 | `@Nested` 按被测方法分组 | `class Create` / `class Update` |

方法名 + 展示名连起来就是一句人话：**「当父栏目不存在时，应该抛出业务异常」**。
