# 07 反模式与常见坑

> 这一篇收录「写了等于没写」的测试反模式和实战中踩过的坑。**每条都是真实现象**，按「现象 → 原因 → 解法」组织。

## 反模式一：只测 happy path

```java
// ❌ 只测了「存在 → 成功」
@Test
void shouldUpdate() {
    when(categoryMapper.selectById(1L)).thenReturn(buildCategory(1L, "旧", null));
    categoryService.update(1L, req);
    verify(categoryMapper).updateById(any(Category.class));
}
```

**问题**：最常出 bug 的恰恰是异常分支 —— 数据不存在、状态不合法、默认值填错。只测 happy path 的用例覆盖率再高也拦不住回归。

**解法**：每个方法至少「正常 + 异常 + 边界」三件套（详见 05 篇场景一）。边界包括空数据、null、不存在。

## 反模式二：断言只写 `assertNotNull`

```java
// ❌ 只验证「不为 null」
assertThat(result).isNotNull();
```

**问题**：组装逻辑错了（比如 VO 里栏目名没填、树挂错父节点）也照样不为 null。等于没断言。

**解法**：断言**具体字段** —— `assertThat(result.getCategoryName()).isEqualTo("公司新闻")`。不为 null 只在「空对象本身有意义」时用。

## 反模式三：用 `assertTrue(xxx == 1)` 断言

```java
// ❌ 失败信息只有 expected: <true> but was: <false>，不知道谁出了问题
assertTrue(result.getCode() == 401);
assertTrue(list.size() > 0);
```

**解法**：全部换成语义化断言（见 04 篇）：`assertThat(result.getCode()).isEqualTo(401)`、`assertThat(list).isNotEmpty()`。

## 反模式四：测试之间共享状态

```java
// ❌ 类字段当「缓存」，用例 2 依赖用例 1 留下的数据
private Article article;
```

**问题**：JUnit 5 每个用例新建实例，字段不会跨用例保留；就算靠 `static` 保留下来，用例顺序一变就挂 —— 测试变成「碰运气」。

**解法**：**每个用例自包含**：given 里自己构造数据。这也让单个用例可以独立运行（IDE 里右键单个用例跑），调试体验完全不同。

## 反模式五：验证实现细节

```java
// ❌ 断言「内部用了什么局部变量」
verify(articleMapper).selectById(1L);
verify(categoryMapper).selectById(10L);
// ...然后断言组装步骤的顺序
```

**问题**：测试和实现绑死。将来实现从「先查文章再查栏目」改成「一次 join」，测试就挂 —— 但它本来没坏任何行为。

**解法**：只断言**输入输出的行为契约**。多依赖协作的用例，打桩两个 Mapper、断言最终 VO 字段即可（05 篇场景三）。

## 反模式六：一个用例断言太多事

```java
@Test
void shouldDoEverything() {
    // 测了创建 + 默认值 + 删除 + 异常，全塞一个方法
}
```

**问题**：失败时不知道哪段逻辑坏了；而且断言堆在一起，前面挂了后面全不执行。

**解法**：一个用例一个行为。20 个小用例的排查成本远低于 3 个大用例。

## 反模式七：mock 被测类自己

```java
// ❌ 用 spy/mock 代替被测类的真实逻辑
CategoryServiceImpl service = spy(new CategoryServiceImpl(...));
doReturn(xxx).when(service).someInternalMethod();
```

**问题**：测的是「mock 出来的假行为」，不是真实代码 —— 测了等于没测。

**解法**：被测对象永远用 `@InjectMocks` 真身，只 mock 它的依赖。

## 坑 1：Mockito 严格模式报 `UnnecessaryStubbingException`

**现象**：`when(...)` 打桩了，测试却直接失败，报 Unnecessary stubbing。

**原因**：`MockitoExtension` 默认严格模式 —— 打桩没被用到就报错，目的是揪出「冗余桩」。

**解法**：
- 排查为什么没走到 —— 可能是分支没覆盖到（好事，补用例）
- 确认确实是分支需要但条件不满足 → 用 `lenient()`，但**不推荐**，先检查设计
- 绝大多数情况：**删掉没用到的桩**

## 坑 2：`when` 打桩了但被测方法拿到 null

**排查顺序**：

1. **参数不匹配**：桩的是 `selectById(9L)`，被测方法调的是 `selectById(1L)`。用 `anyLong()` 或把桩参数和调用参数对齐
2. **注入的不是同一个 mock**：`@InjectMocks` 有多个同类型字段时注入可能错位 —— 检查被测类字段名和 Mock 字段名是否一致
3. **Mockito 无法 mock final/static/private**：默认不行。Spring 的类大多可 mock；如果依赖是 final 类，考虑重构被测代码而不是硬 mock

## 坑 3：测异常时 lambda 里塞了多行

```java
// ❌ 无法确定异常来自哪一行
assertThatThrownBy(() -> {
    articleService.update(1L, req);
    categoryService.delete(1L);
}).isInstanceOf(BusinessException.class);
```

**解法**：lambda 里只有被测调用一行；想验证多个调用，分别写用例。

## 坑 4：测试慢 / 起了 Spring 容器

**现象**：单测跑了好几十秒，日志里看到 Spring Boot 启动信息。

**原因**：误用了 `@SpringBootTest` —— 它会拉起整个容器。Service 单测完全不需要。

**解法**：只用 `@ExtendWith(MockitoExtension.class)`。需要容器的是集成测试（本仓库目前没有）。

## 坑 5：SQL 字符串断言过脆

**现象**：`RoleServiceImplTest` 里 `verify(jdbcTemplate).update(eq("INSERT INTO ..."), ...)` —— 改个 SQL 空格用例就挂。

**权衡**：这是有意为之 —— 原生 SQL 没有 MyBatis 映射层兜底，锁死 SQL 是防「悄悄改坏关联表操作」的契约。代价是改 SQL 要同步改测试。

**解法**：保持现状。这是「用测试锁定无 ORM 保护的 SQL」的必要成本，不要为了省事把 `eq` 换成 `anyString()`。

## 自查清单（提交前过一遍）

- [ ] 每个方法都有异常 / 边界用例，不是只测 happy path？
- [ ] 断言都落在具体字段上，没有一堆 `isNotNull`？
- [ ] 每个用例自包含，不依赖执行顺序？
- [ ] 没 mock 被测类自己？
- [ ] 没有打桩但没用到的 `when`？
- [ ] 没有 `assertTrue(x == 1)` 这类裸断言？
- [ ] `mvn test` 全绿？（运行方式见 08 篇）

## 坑 6：让 AI 做联调时指令模糊 → 子代理雪崩

**现象**：向 Cursor 发「联调测试一下前后端」这类模糊指令，AI 派出大量探索子代理并行摸仓库，子代理互相不共享上下文，挂起、堆积，一个小事被放大成混乱。

**原因**：指令没有边界（环境状态 / 测试范围 / 成功标准 / 变更权限四项都没说），AI 只能「全部探索一遍」。

**解法**：详见 [09-AI辅助联调测试.md](./09-AI辅助联调测试.md) —— 把模糊指令翻译成「环境 + 范围 + 标准 + 权限」齐全的执行题；凡能直接读文件 / 跑命令得出结论的环节，禁止派子代理。

## 坑 7：后台进程挂起，用户不知情

**现象**：AI 后台启动后端/前端服务后直接交差，用户不知道有 java/node 进程在跑，下次启动报「端口被占用」。

**原因**：后台启动（`block_until_ms: 0`）的长驻服务没有「启动声明 + 收尾清理 + 结束确认」三件套，进程脱离用户视线。

**解法**：详见 [09-AI辅助联调测试.md](./09-AI辅助联调测试.md) 第 8 节 —— 启动与清理成对出现；用户可用 `Get-NetTCPConnection` + `Stop-Process` 排查清理。
