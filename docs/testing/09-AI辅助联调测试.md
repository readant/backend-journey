# 09 AI 辅助联调测试

> 这一篇沉淀「怎么指挥 AI 帮你做前后端联调测试」的实战经验。**起因是真实的踩坑**：向 Cursor 发出模糊指令「联调测试一下前后端」，结果冒出大量子代理（subagent）并行探索、互相挂起、越堆越多。
>
> 核心结论一句话：**联调测试不是让 AI 自由发挥的探索题，而是要给 AI 一个带边界、带标准、分步骤的执行题。**

## 1. 现象：模糊指令引发的子代理雪崩

```
用户：「你现在联调测试一下前后端」

AI 的行为：
├── 派 explore 子代理① → 探索前端 admin 仓库
├── 派 explore 子代理② → 探索前端 portal 仓库
├── 派 explore 子代理③ → 探索后端 controller/接口
├── 派 explore 子代理④ → 探索文档/规则/历史记录
├── 全部并行 → 每个子代理各读各的文件、各写各的结论
└── 主代理等子代理 → 子代理互相不共享上下文 → 结论重复/冲突 → 继续派子代理补查
    结果：子代理堆积、挂起，明明是个「起服务 + 打几个接口」的小事，被放大成一场混乱
```

**为什么会这样**：`联调测试一下` 这句话没有告诉 AI 任何边界 —— 环境起了没有？测哪条链路？成功标准是什么？要不要动代码？AI 面对这种「开放式任务」，本能地派并行探索子代理去铺开摸底，每个子代理一个独立上下文，信息无法合并，于是越铺越大。

## 2. 根因分析（为什么子代理会爆炸）

| 根因 | 机制 |
| ---- | ---- |
| **指令没有边界** | 没说环境状态 / 测试范围 / 成功标准，AI 只能「全部探索一遍」 |
| **探索类任务默认并行** | 探索前端 + 探索后端 + 探索文档，天然被拆成多个独立子代理 |
| **子代理信息孤岛** | 每个子代理的上下文独立，探索完把结论丢回主代理，主代理再综合——重复、遗漏、冲突都在这层产生 |
| **子代理与主代理上下文不共享** | 我上一轮联调时**一个子代理都没派**，全部直接读文件 + 跑命令，反而又快又准；凡是「先派子代理摸底」的环节，必然多一层等待和多一份偏差 |
| **挂起 = 等 IO 而非死机** | 子代理可能卡在等某个命令输出 / 等网络请求，主代理只能干等，表现为「堆积」 |

## 3. 正确姿势：把模糊指令翻译成执行题

### 3.1 一句话原则

> **联调测试要告诉 AI：环境什么状态、测什么链路、什么算通过、能不能动代码。** 把这四件事说清楚，AI 不需要派任何探索子代理就能直接干活。

### 3.2 指令模板对比

```
❌ 模糊（触发子代理雪崩）：
   「你现在联调测试一下前后端」

✅ 具体（AI 直接执行）：
   「联调测试 bj-01-cms 前后端。
    环境：MySQL 已启动（bj_cms 库有种子数据）、后端与前端均未启动。
    步骤：① 后台启动后端 mvn spring-boot:run；② 等 Health 返回 code=200；
    ③ 用 curl 测 /api/v1/admins/login 拿 token；④ 带 token 测文章分页/栏目树/看板；
    ⑤ 验证 admin(3002) 与 portal(3001) 的 vite 代理转发；⑥ 全程不要修改任何代码，只测不改。」
```

差在哪：右边把 AI 的每一步都框死了，AI 不需要「探索该干嘛」，只需要「执行」。

### 3.3 四条边界参数（下指令前问自己）

| 参数 | 必须说清 | 否则 AI 会 |
| ---- | -------- | ---------- |
| **环境状态** | MySQL / 后端 / 前端 是否已在运行 | 重复启动、端口冲突、误判「服务挂了」 |
| **测试范围** | 测哪些接口 / 哪些页面，不测哪些 | 全仓库地毯式扫一遍 |
| **成功标准** | 什么结果算通过（code=200？页面 200？） | 打几个接口就交差，或永远觉得没测完 |
| **变更权限** | 只测不改 / 允许改代码修 bug | 擅自改代码、改数据库，风险失控 |

## 4. 什么时候可以用子代理，什么时候禁止

| 场景 | 是否派子代理 | 说明 |
| ---- | ------------ | ---- |
| 起服务、打接口、验证返回 | ❌ 禁止 | 直接跑命令 + 断言，毫秒级出结果 |
| 在**已知文件**里查某个符号 | ❌ 禁止 | 直接搜（Grep/Glob），一个调用的事 |
| 需要**全仓摸底**「有哪些接口/组件」 | ✅ 允许，最多 2~3 个 | 每个子代理任务边界必须写死（如「只列 admin 的 src/apis/**」） |
| 并行跑互不依赖的构建/测试 | ✅ 允许 | 但每个都该是确定性命令，不该是开放式探索 |

> 红线：**凡是可以直接读文件 / 跑命令得出结论的，就不要派子代理。** 子代理是「地图很大、一次只能看一角」时用的，不是给 AI 偷懒摸鱼用的。

## 5. 子代理已经堆积 / 挂起时的处置

```
1. 识别：看到 AI 在连续派「探索」子代理、反复读同一批文件、迟迟不执行命令
2. 干预：直接发「停下，不要再用子代理。按我说的做：先查 X，再跑 Y」
3. 收束：给一个更具体的指令（用 3.3 的四条边界参数重新描述任务）
4. 验证：确认没有遗留的后台进程（终端面板逐条检查，卡住的 kill 掉）
5. 复盘：把这次的经验补进本文档「现象→原因→解法」
```

## 6. 联调测试的最小执行模板（直接抄）

```
【任务】{联调范围，如：登录 → 管理端核心接口 → 前台首页}
【环境】{MySQL 状态 / 端口占用 / 服务是否已启动}
【步骤】1. {启动后端} 2. {验证 Health} 3. {接口链路} 4. {前端代理} 5. {收尾：清理进程}
【成功标准】{具体到 code / 数据量 / 页面状态码}
【权限】{只测不改 / 可改 }
```

## 7. 反模式速查（本篇对应的 07 篇条目）

- 指令不给边界 → AI 派探索子代理 → 雪崩（本节 1~2）
- 能用命令直接验证的环节派了子代理 → 多一层等待 + 信息偏差（本节 4）
- 子代理挂起不干预 → 堆积恶化 → 直接打断重下指令（本节 5）

## 8. 后台进程挂起，用户不知情（真实踩坑）

> 这是另一类高频问题，和子代理雪崩同根同源：**AI 为了「后台启动服务」把进程丢到后台，却没人告诉用户「有三个服务在跑」。** 用户关掉 Cursor 或新开会话后，`java` / `node` 进程继续占着 8080/3001/3002 端口 —— 用户下次启动时报「端口被占用」才知道有幽灵进程。

### 8.1 现象

```
用户让 AI「联调一下前后端」
AI 执行：
├── mvn spring-boot:run     → 丢后台，java 进程占 8080
├── npm run dev (admin)     → 丢后台，node 进程占 3002
└── npm run dev (portal)    → 丢后台，node 进程占 3001
会话结束后：
├── 用户不知道有 3 个进程在跑
├── 端口被持续占用，下次启动报错
└── 进程在任务管理器里叫 java/node，难以一眼认出是哪个项目的
```

**为什么用户不知道**：后台启动的服务，输出进了终端日志文件而非用户可见的界面；对话结束时也没有任何「清理进程」的收尾步骤。

### 8.2 根因

| 根因 | 说明 |
| ---- | ---- |
| **后台 ≠ 无主** | AI 把长驻命令丢后台后，没有建立「谁启动了、何时结束、谁来收」的责任闭环 |
| **收尾动作缺失** | 联调测完直接交差，没有「停掉我启动的服务」这一步 |
| **进程不可见** | `java`/`node` 进程名不体现项目，用户看任务管理器也认不出 |

### 8.3 解法：启动与清理成对出现

**AI 侧铁律**：凡是 `block_until_ms: 0` 后台启动的长驻服务，必须同时做到三件事：

1. **启动时声明**：告诉用户「我启动了 X（端口 Y），结束时我会停掉它」
2. **结束时清理**：任务完成前，用 `Get-NetTCPConnection` 找到占用端口的进程并 kill，确认端口释放
3. **收尾确认**：结束时明确说「已停止的服务清单 + 端口已释放」

**用户侧排查命令**（Windows）：

```powershell
# 查指定端口被谁占用
Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 8080,3001,3002 } | Select LocalPort, OwningProcess
# 查 java/node 进程
Get-Process -Name java,javaw,node | Select Id, ProcessName, StartTime
# 按 PID 停掉（先确认是你要停的）
Stop-Process -Id {PID} -Force
```

### 8.4 联调收尾清单（测试完成后必查）

- [ ] 我启动的后端 / 前端服务是否已停止？
- [ ] 占用端口是否已释放（8080/3001/3002 无监听）？
- [ ] 有没有残留的 `java` / `node` 进程？
- [ ] 启动与清理是否成对出现、向用户声明过？

> 补充：已实测确认 —— 上一轮联调启动的三个服务（8080/3001/3002）现已全部停止、端口释放、无残留进程。这条经验就是从那轮「用户不知情」的教训里提炼的。
