# 10 改完代码怎么测（变更驱动测试）

> 改了一部分功能、加了新功能，要不要全测？测哪些？这一篇给出标准答案。
> 核心一句话：**不是全量回归，是按影响面分层测试**——但单元测试层永远全量跑（它秒级完成，代价最低）。

## 1. 三层测试，对应三个问题

| 层 | 回答的问题 | 触发时机 | 成本 |
| ---- | ---- | ---- | ---- |
| 单元测试（JUnit 5） | 我的代码逻辑对吗？ | 每次改动，**永远全量跑** | 秒级，几乎免费 |
| 接口冒烟（curl / 脚本） | 分层组装起来通吗？ | 每次改动，**按影响面选接口** | 分钟级 |
| 手工/浏览器 UI | 用户实际用起来对吗？ | 涉及前端展示、交互、流程时 | 分钟级 |

三层是递进关系，**每一层通过才进下一层**，不要跳过单测直接开浏览器。

## 2. 影响面判断表（改了 X，要测 Y）

判断依据只有一个：**改了什么，谁依赖它**。

| 我改了 | 必须测 | 建议顺带看 |
| ---- | ---- | ---- |
| 某个 Service 方法 | 该 Service 的测试类全绿（`mvn test`） | 调用它的其他 Service / Controller |
| 某个 Mapper | 调它的 Service 测试类 | SQL 相关的接口冒烟 |
| Controller | 该接口的 curl 冒烟（改一个端点测一个） | 前端对应页面 |
| 公共组件（R、BusinessException、全局异常处理器） | **全量单测** + 所有接口冒烟抽测 2~3 个 | 异常路径（故意传错参数看返回） |
| 表结构 / Flyway 迁移 | 全量单测 + **全链路冒烟**（涉及该表的接口全测） | 前端列表/详情/编辑 |
| 仅新增代码（不动已有） | 新增的测试类 + `mvn test` 防回归 | 新接口冒烟 |

规律：**改动越靠底层、影响面越大**（公共组件、表结构 = 全仓受影响）；改动越靠上层、影响面越小（单个 Controller 端点 = 只测它自己）。

## 3. 三步走流程

### 第一步：单测（永远做）

```bash
cd bj-01-cms
mvn test
```

- 全量跑，不挑用例。74 个用例秒级完成，没有理由不全跑。
- 新增功能 → 先按 `docs/testing/05` 的模板补核心 Service 测试，再跑。
- 单测红了 → 修好再往下走，红着进接口层是浪费时间。

### 第二步：接口冒烟（按影响面选）

启动后端：

```bash
mvn spring-boot:run
```

用 curl 或脚本打接口，只测影响面内的：

```bash
# 冒烟模板：登录拿 token → 打目标接口
curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

冒烟要点：

1. **改哪个端点，测哪个端点**，至少覆盖：正常路径 + 一个异常路径（缺参数/不存在 ID）。
2. 看到返回体 `code=200` 只是「通了」，还要看 `data` 内容对不对。
3. 涉及公共组件 → 抽测 2~3 个不同业务的接口，确认没被带崩。
4. 复杂多步流程（登录→创建→查询→更新→删除）写成一个脚本串起来跑。

### 第三步：UI 走查（涉及前端时）

前端展示/交互变了才做这步，不用每次都开浏览器：

1. 启动后端 + 对应前端（admin 3002 / portal 3001）。
2. 打开页面，走一遍改动涉及的入口：列表 → 详情 → 编辑/新增 → 删除。
3. 重点看：数据渲染对不对、操作后列表有没有刷新、报错有没有提示。

## 4. 新增功能的完整流程示例

场景：给 Article 新增「批量发布」功能。

```text
1. 写代码：ArticleService 新增 batchPublish，Controller 新增 POST /api/v1/articles/batch-publish
2. 补测试：ArticleServiceImplTest 新增 @Nested 测试类（正常批量 + 含不存在 ID + 空列表边界）
3. 跑 mvn test → 全绿
4. 冒烟：curl 登录 → 调批量发布（2 篇正常 + 1 篇不存在 ID）→ 验证 data 与异常分支
5. UI：portal 文章列表页点「批量发布」按钮 → 确认结果提示
6. 收尾：提交前 mvn spotless:apply（见 git-workflow 规范）
```

## 5. 高风险变更，先问再测

以下变更**动手前必须先和用户确认方案**（`docs/standards/version-evolution.md` 也有同样约束）：

- 数据库表结构变更
- API 请求/响应结构变化
- pom.xml 新增第三方依赖
- 超过 50 行的重构
- 公共组件接口变更

这类变更的测试范围最大、返工成本最高，方案先对齐，避免测完白测。

## 6. 与 09 篇（AI 辅助联调）的分工

- 本篇讲「人改完代码自己怎么测」的分层流程。
- 09 篇讲「把联调交给 AI 时，怎么下指令才不翻车」——本质是把这个三步流程翻译成给 AI 的执行任务，四个边界（环境状态 / 测试范围 / 成功标准 / 变更权限）一个都不能少。

自己改的代码先按本篇走完三步，再考虑要不要用 09 篇的方式让 AI 加速执行。
